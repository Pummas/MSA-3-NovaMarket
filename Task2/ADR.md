## Решение

### Выбран паттерн: **CQRS**

Сценарий «Просмотр истории покупок» - **read-heavy** и требует агрегации данных из нескольких доменов (заказ, оплата,
доставка). Прямое чтение из Order + Payment + Delivery потребовало бы синхронных вызовов и давало бы медленный и хрупкий
отклик.

**CQRS** позволяет:

- Разделить запись (Order, Payment, Delivery) и чтение (History Service).
- History Service строит **денормализованную read-модель**, оптимизированную под запросы списка и деталей.
- Все обновления приходят **асинхронно через события** - сервисы-источники не знают о History.
- Отклик на чтение ≤ 0,3 сек достигается за счёт единого индекса и отсутствия сетевых вызовов между сервисами.

### Логика решений

1. **CQRS.** History Service - отдельная read-модель, наполняемая событиями. Запись остаётся в Order / Payment /
   Delivery. Чтение полностью изолировано.

2. **Денормализация в History DB.** Одна запись = один заказ со всеми атрибутами: сумма, дата, способ доставки, способ
   оплаты, финальный статус, товары. Это позволяет получить список заказов одним `SELECT` без джойнов и сетевых вызовов.

3. **Read-index.** Для быстрого листинга по `userId` - индекс `(userId, created_at DESC)`. Для деталей - `orderId` как
   первичный ключ.

4. **Eventual consistency.** History отстаёт от источников на время обработки события (обычно десятки миллисекунд). Для
   сценария «посмотреть историю» это приемлемо.

5. **Receipt Service вынесен отдельно.** Генерация PDF - CPU-тяжёлая операция. Вынос позволяет масштабировать её
   независимо и не блокировать чтение истории.

6. **Повтор заказа.** Реализуется на клиенте: `POST /cart/items` с товарами из истории. Ничего в архитектуре не
   меняется.

7. **Отзыв о товаре.** Идёт напрямую в Catalog Service - не часть read-модели истории.

## Альтернативы

### Альтернатива 1. API Composition

API Gateway при запросе истории синхронно вызывает Order, Payment, Delivery, Catalog и собирает ответ.

**Плюсы:**

- Нет дублирования данных - всегда актуальная информация
- Не нужен отдельный сервис
- Проще реализовать на старте

**Минусы:**

- **Не проходит по SLA:** каждый запрос = 4+ сетевых вызова, при нагрузке latency растёт линейно
- Каскадные отказы: если Delivery недоступен - вся история не грузится
- N+1 запросов к Catalog для списка заказов (товары каждого заказа)
- Gateway превращается в оркестратор - сильная связанность

**Вердикт:** ❌ не выдерживает требования ≤ 0,3 сек на 98% и хрупко.

### Альтернатива 2. Event Sourcing

Хранить все события заказа как единственный источник истины, восстанавливать состояние заказа на лету.

**Плюсы:**

- Полный аудит: любой заказ можно «перемотать» на любой момент
- Идеально для аналитики и антифрода
- Естественно сочетается с EDA

**Минусы:**

- Сложность: снапшоты, версионирование событий, миграции схем
- Долгое восстановление состояния без снапшотов - не для read-heavy сценариев
- Избыточно для MVP и текущей задачи
- Требует пересмотра всей модели заказа (у нас уже есть state-based Order DB)

**Вердикт:** ⚠️ мощно, но избыточно. Не подходит по типу задач, которая решает система.

## Недостатки, ограничения, риски

### Недостатки

1. **Eventual consistency.** История отстаёт от источников на время обработки события. Пользователь может не увидеть
   заказ сразу после оформления - потребуется UI-заглушка «Заказ обрабатывается».
2. **Дублирование данных.** История хранит копию данных из Order, Payment, Delivery. Растёт объём хранилища.
3. **Сложность миграций.** Изменение схемы событий требует версионирования и обработки старых событий в History Service.
4. **Отдельный сервис.** Больше кода, деплоя, мониторинга.

### Ограничения


1. **История зависит от событий.** Если событие потеряно - History его не восстановит. Требуется DLQ и идемпотентность
   обработчиков.
2. **Порядок событий.** Kafka гарантирует порядок только в пределах партиции. Партиционирование по `orderId` -
   обязательно.
3. **Регионы.** Для мультирегиональности потребуется отдельный History DB на регион и маршрутизация запросов.

### Риски

1. **Потеря событий.** Если consumer упал и не закоммитил offset - потеря данных истории. **Митигация:** DLQ, retry с
   экспоненциальной задержкой, идемпотентные обработчики.
2. **Рассинхрон с источниками.** Если Order DB обновилась, а событие не опубликовалось - история «застрянет». *
   *Митигация:** outbox pattern на стороне источников.
3. **Перегрузка History DB при росте.** При 40k+ заказов в день таблица быстро растёт. **Митигация:** партиционирование
   таблицы по месяцу, архивация старых заказов в холодное хранилище.
4. **Скачивание чеков.** Receipt Service может не успеть генерировать PDF под нагрузкой. **Митигация:** асинхронная
   генерация + кэш в S3.
5. **Изменение схемы событий.** Новые поля в событиях сломают старые обработчики. **Митигация:** версионирование
   событий (`OrderCreated.v2`), schema registry (Avro/Protobuf).
